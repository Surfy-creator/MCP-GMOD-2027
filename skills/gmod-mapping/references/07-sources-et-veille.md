# Sources, verified facts and monitoring log

Contents: 1. How to use this page · 2. Sources to monitor · 3. Verified facts (dated) · 4. Open points to verify · 5. Weekly monitoring protocol · 6. Log

## 1. How to use this page
- Before stating a fact **that changes over time** (Hammer++ version, compile option, engine limit, tool format), check the verification date here; if it is more than a few weeks old, re-verify against the source.
- Facts are **summarized in my own words**, with the source and date. No copied text: point to the page instead.
- The weekly task updates sections 3, 4 and 6, fixes the other references when a fact has changed, and dates every change.

## 5. Weekly monitoring protocol
1. Read sections 3 and 4 of this page to know what to verify; note today's date.
2. For each source in table 2: open the page (web search + reading the page), note what has changed since the last verification date. For GitHub repositories: latest releases and dates, compatibility changes. For communities: notable new guides on Hammer/Hammer++, GMod mapping, Source modeling, textures/normal maps.
3. Sort: **changes a fact in the skill** (fix the relevant reference), **useful news** (add it as one line to the log), **noise** (ignore).
4. Update: section 3 (new or changed facts with date and source), section 4 (remove what is resolved, add new doubts), section 6 (one short entry). Fix the other references if a fact has changed (for example a compile option).
5. Never copy long texts: summarize, cite the page.
6. If a source is inaccessible or ambiguous, write "not verified" rather than guess. If a verification risks relying on unconfirmed facts (a source that is long to read in depth, several sources to cross-check), delegate it to a subagent that returns sourced claims, then cross-check its key points.
7. Keep the log to at most 12 entries: merge the oldest into a single summary line.
8. Deliver: the updated skill (`gmod-mapping.skill`) and a monitoring summary (news, corrections, open points).
